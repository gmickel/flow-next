# Judge at dispatch

Before each worker spawn, call `$FLOWCTL judge --preset tier --task <task-id> --json` once. Pass the explicit invocation model with `--explicit-model`, the routing block's fast model with `--fast-model`, and the role's pinned model with `--role-model` when present. Pass `--can-spawn-model` / `--can-bridge` only for host-verified reach. Scouts still use `--state-file` for their actual bounded assignment (`task_title`, `task_body`, `acceptance`, `touches_count`, `has_quick_commands`, `repo`), with the same reach flags. Keep this result for the admission; never reroute a running worker or repeat the rolling decision at Phase 3c.

Use the returned `tier_line`, `spawn_model`, and `implementer`. Set `spawn_model_args` to `{"model": result["spawn_model"]}` when non-null, otherwise `{}`. The renderer preserves explicit model choices and pinned roles; unavailable judge answers keep the session tier.

Expand `spawn_model_args` into the Task invocation so the selected model reaches its **`model` parameter**; on another host map that field to its equivalent spawn-model parameter. Also pass `IMPLEMENTER: <implementer>` in the worker prompt when set. The prompt alone never selects a native model. For bridge-only reach, leave the native spawn unchanged and let worker Phase 1b resolve the `IMPLEMENTER` bridge. An explicit invocation remains authoritative; the selector never changes its existing spawn routing. Scouts use the same selection with the host's read-only restrictions preserved and `role_model` set from the scout's role definition: a pinned role keeps its model and the `Tier:` line names it, since a spawn parameter would not change what runs; on bridge-only reach without a scout bridge, retain the existing scout model and state that limitation.

Print `tier_line` at dispatch and retain it in the task's done summary (or scout findings). After return append `(model: <actual_model>)` only when the returned model is backed by host execution metadata or the worker's actual bridge command. Missing model evidence gets no model annotation; never copy the requested model into the actual-model field. A long-running recommendation is advisory and creates no bridge or approval requirement.
