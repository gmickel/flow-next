# Flow-Next docs

> **Codex install note:** when YOU run a flow-next command on THIS Codex install, invoke it as `$flow-next-<name>` (or pick it from the skills dropdown) wherever this page writes `/flow-next:<name>` — and when the written name itself already starts with `flow-next-` (e.g. `/flow-next:flow-next-drive`), the prefix is not doubled: invoke `$flow-next-drive`. Passages describing OTHER hosts (Claude Code `claude -p` / `/loop` examples, Grok, Cursor, OpenCode sections) document those hosts' own syntax and are quoted verbatim — do not convert them.


The offline-resilient reference for flow-next — **repeatable agentic engineering**: durable specs, re-anchored workers, adversarial reviews, receipts. Each file here is self-contained, terse, and offline-readable. Cross-links use relative repo paths — fork-survivable, no external URLs.

**Start here by intent:**

- *"What is this and how do I install it?"* → [root README](https://github.com/gmickel/flow-next/blob/main/README.md) — pitch, tenets, install, 5-command happy path.
- *"What skills exist?"* → [`skills.md`](skills.md) - all 30 skills, triggers, one-liners.
- *"Do I need all of this?"* → [`running-lean.md`](running-lean.md) — no. The base loop is spec → plan → work; everything else is a layer with a stated cost, a trigger, and a manual invocation.
- *"Which stages does THIS change need?"* → [`pipeline-variations.md`](pipeline-variations.md) — five worked routes (epic → docs chore), selected by risk and unknowns, never by size.
- *"How do we adopt this as a team?"* → [`teams.md`](teams.md) — handover objects, Spec-as-PR, adoption ladder.
- *"How do I run it autonomously?"* → the pilot/land skill pages below (`ralph.md` documents the deprecated harness).
- *"Which model does what, and how do I change that?"* → [`orchestration.md`](orchestration.md) - the tier vocabulary and routing precedence, the routing block in your own instruction file, review backends, the bridge route, loop chaining (including unattended chart driving).
- *"How does my harness reach another model for a tier?"* → [`reach/README.md`](reach/README.md) — one page per harness; undetectable harness → the generic page.
- *"What's every flag on every command?"* → [`flowctl.md`](flowctl.md) (includes the full `flowctl chart` contract).
- *"This idea is too big / still unclear before capture?"* → [`../skills/flow-next-chart/SKILL.md`](../../skills/flow-next-chart/SKILL.md) - optional `/flow-next:chart` decision-map discovery; never mandatory.
- *"Not sure which pre-build path is smallest?"* → [`../skills/flow-next-guide/SKILL.md`](../../skills/flow-next-guide/SKILL.md) - `/flow-next:guide` router.

> For the repo's strategic intent see [`../../../STRATEGY.md`](https://github.com/gmickel/flow-next/blob/main/STRATEGY.md). For vocabulary discipline — the load-bearing terms (Spec, Task, R-ID, Chart, Receipt, Gate, plan-sync, …) and the synonyms to avoid — see [`../../../GLOSSARY.md`](https://github.com/gmickel/flow-next/blob/main/GLOSSARY.md); it is a dictionary, not an encyclopedia, and the concepts themselves are explained on the pages below. The retired long-form glossary is archived at [`../../../agent_docs/archive/GLOSSARY-full.md`](https://github.com/gmickel/flow-next/blob/main/agent_docs/archive/GLOSSARY-full.md).

## Notable updates

Append-only list of **behavior-affecting changes and new opt-in defaults**. Newest first. Not a changelog — one line each, plus how to enable. Seeded by fn-134; later releases append.

**Format (keep this shape):**

```
- **`config.key` or feature name** — one-line what changed / why it matters. Enable: `command or config`. Details: [link](path).
```

- **Excused completion reviews: `completion_review_status: not_required` (4.6.0)** — work's 3g policy skip now records the excused decision and every gate (projection, `next --require-completion-review`, pilot, Ralph) treats it as satisfied instead of re-requesting the review; surface-changing edits re-arm it. Always on. Details: [flowctl.md](flowctl.md).
- **Reviewer verification budget (4.6.0)** — impl and completion review rounds verify via focused, evidence-named suites; the full suite runs only at the run's final gate. Always on (prompt rail). Details: [orchestration.md](orchestration.md).
- **`planSync.enabled` becomes opt-in (4.5.1)** - fresh installs no longer run the per-task plan-sync pass by default: on most specs it finds nothing to change, and manual `/flow-next:sync` keeps the full capability on demand. Existing configs are untouched; setup still asks. Rolling-frontier's prerequisite is now the default state. Enable (the old behavior): `flowctl config set planSync.enabled true`. Details: [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md), [`running-lean.md`](running-lean.md).
- **`/flow-next:work-rolling` - rolling-frontier scheduling beta (4.5.0)** - an experimental, user-invoked variant of work that admits the next eligible task the moment any worker returns instead of waiting at wave barriers (52.1% work-phase wall saving at quality parity in the pre-registered fn-203 eval; the faster shared-checkout arm was rejected for buying speed with thinner tests). Same gates, receipts, and reviews; pilot/land/Ralph stay on canonical work. Enable: `/flow-next:work-rolling <spec-id>` (repos with plan-sync on must first `flowctl config set planSync.enabled false`). Details: [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md), [`troubleshooting.md`](troubleshooting.md).
- **A run stops paying twice for the same test evidence (4.3.1)** - when a review fix loop's post-fix run passes the full-gate command at the committed fix HEAD it writes the green receipt the later Verify honors, so a NEEDS_WORK -> SHIP cycle no longer repeats 2-10 minutes of identical tests; and on a multi-task run a worker can inherit the previous task's proven-green baseline when the Quick commands, HEAD, and Touches all check out. Fail-closed both ways: focused suites never mint a full-gate receipt, the first task's baseline always runs, and lint always runs. Enable: nothing - default behavior. Details: [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md).
- **Capture and plan tell you the smallest sufficient next step (4.4.0)** - each closer prints one advisory `Recommended next:` line above its unchanged menu, judged from the spec or plan just produced against [`pipeline-variations.md`](pipeline-variations.md)'s risk-and-unknowns selector (capture: interview vs plan vs minimal-plan; plan: plan-review vs straight-to-work, review skips reserved for the two documented ceremony shapes; chart never a target, `/flow-next:guide` on conflicting signals; autonomous runs unchanged). The PR's external review also hardened the Codex install: docs ship under an owned `docs/flow-next/` namespace (installer can never touch non-owned files, sentinel-tested), every mirrored docs link resolves or is absolute (closure guard), and each page opens with a Codex invocation banner. Enable: nothing - default behavior. Details: [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md), [`pipeline-variations.md`](pipeline-variations.md).
- **Less duplicated review and plan-sync work per run (4.2.2)** - three wall-clock fixes with no change to what reviews check: a single-task spec whose only task already holds a per-task SHIP and covers every spec R-ID skips the completion review (recorded skip line, never silent); plan-sync dispatches once per resolved wave with the full completed-task set (same downstream scope, per-task drift verdicts preserved); and a dep-independent task MISSING its `**Touches:**` line on a multi-task spec is now a plan-review finding (omission silently forces serial dispatch), with pilot echoing the work stage's `Sequential fallback:` reason. Also documented: `.git/flow-state` is shared across worktrees - set `FLOW_STATE_DIR` (outside the tree) per agent for concurrent same-repo pipelines. Enable: nothing - default behavior. Details: [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md), [`flowctl.md`](flowctl.md).
- **OpenCode is a first-class harness (4.3.0)** - `./scripts/install-opencode.sh` scatters canonical skills + generated agents/commands into `~/.config/opencode/` with a deterministic ownership manifest; setup detects the host via that manifest and runs like every other host; multi-agent fan-out, codex review, and host review (agent-pinned reviewer, fail-closed degradation) verified live. Slash form is flat `/flow-next-<name>`; Ralph intentionally not built; the flow-next-opencode port is superseded. Enable: run the installer. Details: [`platforms.md`](platforms.md#opencode), [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md).
- **Setup prices each opt-in in its question; `host` on every review menu (4.2.1)** - the review-backend question states where the time goes (each review round is a serial pass the pipeline waits on - usually the largest wall-clock item in a run), the `None` option says what still gates a run and what stops being checked, and the Claude Code / Droid / Codex menu now offers `Host` - the host-native reviewer that keeps every gate with no second CLI, pinned via one `reviewer:` routing-block line. Enable: nothing - next `/flow-next:setup` run on an unset key. Details: [`running-lean.md`](running-lean.md#turning-the-dial-none-and-host), [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md).
- **land asks the human reviewer when it is their turn (4.2.0)** - `land.requestReviewers` (§2.6b → §3.4b, opt-in): a csv of GitHub logins / `org/team` slugs / the literal `codeowners`. Exactly when a human review is the only missing merge input (CI green, no open threads, signal unsatisfied under `approve`/`<login>` or `REVIEW_REQUIRED` under `silence`), land flips a draft PR to ready and requests the list minus the PR author - once per PR per head SHA, recorded in the land ledger; a failed request records the head and reports `reviewers=failed:<reason>`, never `BLOCKED`. It never gates a merge (`reviewSignal` does); `--dry-run` reports `reviewers=would-request`. Enable: `flowctl config set land.requestReviewers "alice,org/platform"`. Details: [`flowctl.md`](flowctl.md), [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md).
- **Pilot composes with worktrees; tracker states readable without writes (4.1.0)** - pilot's `plan`/`plan-review` stages no longer demand the default branch (they probe the current branch for an open PR and plan in place - the one-worktree-per-spec setup now runs the full loop), and merged gate PRs on a reused branch classify `make-pr` via head identity instead of dead-ending `NEEDS_HUMAN`. New read-only `flowctl tracker wire list-states` (Linear/Jira) lists workflow states with a trustworthy `complete` flag - detection never writes; `tracker resolve` stays the repair verb. Also: a review round that delivers no verdict can no longer wedge a spec's reviews (`REPLAY_REQUIRED` loop; pre-4.1.0 wedges self-heal on the next dispatch). Enable: nothing. Details: [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md), [`tracker-sync.md`](tracker-sync.md), [`troubleshooting.md`](troubleshooting.md).
- **Pipeline variations - the stage axis gets an in-repo owner** - a new [`pipeline-variations.md`](pipeline-variations.md) shows five worked routes through the menu (full epic down to docs-chore) and names the real selector: risk and knowns/unknowns, never size - each stage either converts an unknown into a known or bounds the cost of being wrong, and a stage with neither left is ceremony. Prospect/chart are framed as upstream discovery an organization has often already done under another name (roadmap, brief, groomed backlog). The variants are worked examples, not tiers; every route keeps the evidence/gate/review contracts and records skips as `skipped(reason)`. Enable: nothing - documentation only. Details: [`pipeline-variations.md`](pipeline-variations.md).
- **Copy-less installs: flowctl resolves from the plugin install on every host (4.0.0)** - your repos no longer carry flowctl copies: every skill resolves the bundled `flowctl` through a three-rung chain (plugin-root env var on Claude Code / Droid; the plugin root derived from the loading skill's own path on Cursor / Grok; `$CODEX_HOME` on Codex), so a plugin update never requires re-running setup in any repo again. Setup is one mode and writes zero copies; on a repo with leftovers (`.flow/bin/`, `.flow/templates/spec.md`, `.flow/usage.md`) it offers to delete them - nothing reads them, deleting changes nothing observable (a customized spec template is detected and never deleted; copy it to a repo-root `SPEC.md`). `flowctl setup-mode` is gone; old stamps are inert. Enable: nothing - delete your copies whenever convenient, or let `/flow-next:setup` offer it. Details: [`platforms.md`](platforms.md), [`troubleshooting.md`](troubleshooting.md#i-have-flowbin-from-an-old-install), [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md).
- **Packaged codex delegation removed (4.0.0)** - the `work.delegate*` config subsystem (fn-55) is deleted; implementation offload is the routing block's `implementer` tier plus the bridge recipes (`flowctl usage`), which is what superseded it in practice. The two things worth keeping survive in prose: the bridged child writes code while the host keeps git, judgment, and the verdict; and clear, well-scoped work runs well on a value-tier implementer, escalate for gnarly tasks. A config still carrying the removed keys gets one non-blocking advisory and runs unchanged. Enable: n/a - removal; the migration is one routing-block line. Details: [`orchestration.md`](orchestration.md#implementation-offload--the-bridge-route), [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md).
- **Routing by intent: four tier names, a reach page per harness, zero shipped model ids (4.0.0)** - say what KIND of model a job wants (`reviewer` / `implementer` / `fast scout` / `thinking scout`, or unset - the session model, and the default) and write the model names once, in your own `CLAUDE.md` / `AGENTS.md`, verified against your own account. Removed with the machinery: the setup probe-and-pin ceremony, the `models.roles` role map with its `verifiedAt` / `verifiedWith` staleness stamps, and every shipped model identifier outside the orchestration reference page and the `review.backend` grammar. Resolution is one sentence at each dispatch site - explicit instruction, then your routing block, then the agent default, then the session model - and an unreachable model falls back to the session model with one note, never a failure. Enable: `/flow-next:setup` writes the block commented out; fill in a tier line. Details: [`orchestration.md`](orchestration.md#tiers--what-kind-of-model-a-job-wants), [`reach/README.md`](reach/README.md), [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md).
- **Locked-down repos: the merge-identity seam, server-side catch-up, and a tail that finishes (3.34.0)** - `FLOW_PR_MERGE_CMD` (env-only, #277's merge-side counterpart, stderr-verbatim contract); the `rebase` action is now server-side `catch-up` via `gh pr update-branch` - land never rebases or force-pushes again (removes the #302 orphaned-evidence cause; repeated refusals escalate bounded); the post-merge tail runs release + tracker before the persist-push, so a PR-only base costs a bookkeeping note, not a stuck board. Also: fresh-clone `validate` is meaningful (durability-aware status findings), `done`/`block` report `modified_paths` + a dirty-receipt advisory, `config_lock` reports what it observed instead of a phantom holder, and review-attempt rows record the model/effort that actually ran. Enable: nothing - `FLOW_PR_MERGE_CMD` opt-in by env. Details: [`skills.md`](skills.md), [`flowctl.md`](flowctl.md), [`architecture.md`](architecture.md), [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md).
- **Concurrent task waves are reachable by default (3.33.0)** - planning now writes a `**Touches:**` line on every task (declare wider rather than omit when uncertain), which is the declaration wave dispatch is fail-closed on; while it was optional, waves fired far less often than the task graph allowed - and in this repo's own recent specs, not at all. Two preconditions are now stated where the conductor reads them: commit the spec/task files before creating wave workspaces (a workspace is branched from a commit, so an uncommitted spec leaves every parallel worker unable to re-anchor), and normalize each task's evidence to the INTEGRATED commit SHAs at the join (handover SHAs die with the workspace and `flowctl validate` then reports them orphaned). Enable: nothing - default behavior; a wave still requires same spec, size <=3, no dependency path, disjoint declarations, and no always-serial paths. Details: [`teams.md`](teams.md), [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md).
- **`/flow-next:visual` — review a plan, task, diff, or the conversation at a glance (3.32.0)** - a compact markdown digest (task tree, planned file-layout diff, R-ID coverage line, diff-fenced sketches) rendered in plain fenced blocks that colorize on every host; capture/plan/interview offer it at read-back, and make-pr's `## Structural changes` may emit a diff-fenced sketch where mermaid is weakest (mermaid-rules §8). Read-only, chat-only; explicit-only on Codex (`$flow-next-visual`, see [`platforms.md`](platforms.md)). Enable: nothing - `/flow-next:visual <spec|task|range|topic>` or plain language ("show me", "too much text"). Details: [`skills.md`](skills.md), [CHANGELOG](https://github.com/gmickel/flow-next/blob/main/CHANGELOG.md).

## Conventions

- **R17 cross-link discipline.** Each doc here is a self-contained reference. Canonical sources (`templates/spec.md`, `scripts/sync-codex.sh`, `STRATEGY.md`, `GLOSSARY.md`) are linked, never re-embedded.
- **Relative paths only.** No absolute `github.com/...` URLs anywhere in this tree — fork-survivable + offline-readable.
- **Length discipline.** Reference shape (tables, lists, schemas first; narrative second). Brevity beats completeness.
