# Orchestrate

Reach another model or harness for review, a read-only scout, or a build the person asked to hand over.

A stated preference is not a fact about availability. Ask the active harness what it can reach and resolve a person's words at run time rather than copying model identifiers or flags from documents. Unless the instruction files or the request say otherwise, review with a model from a different family than the one that built the change, in this order of preference: GPT-6.2 Sol at medium effort, Opus 5.5 at high, Gemini 4 Neon at high, Grok 4.7 at high, Muse Wonder 1.0 at high. Take the first of them this host can itself run and use the host's own subagent for it, because the host can enforce read-only tools and no second login is needed; when the host offers none of them, take the first that another installed tool can reach. Use the named version and effort exactly; a different version or effort is a different model, so move down the list. Say which model and effort reviewed and by which route.

Two routes exist: a parameter on the host's subagent spawn, or a second command-line tool run non-interactively. Where the host's subagents cannot take a model, a second process of the same host on the chosen model is still the host's own route. Ask the tool for its current options and guard its traps: use read-only or sandboxed mode for a reviewer; a headless reviewer cannot ask for permission, so allow it read-only commands for that run or it returns nothing; close standard input so a non-interactive tool does not hang waiting for input; run long calls in the background and wait with a deadline so they outlast shell limits, and when nothing will wake the session again (a headless or unattended run) wait for the reviewer before ending the turn; pass the brief as a file and capture output to a file in a temporary directory outside the repository so a review leaves the working tree untouched; keep the session id to resume later rounds; and tell it in the brief not to route through Flow, since it reads this repo's instruction files too.

Send a self-contained brief naming goal, paths, rules, and expected output. This session keeps scope, git, review, and the verdict; a handed builder may commit checkpoints on the named branch and never pushes, rewrites history, or issues a verdict.

An optional budget word (`large`, `medium`, or `small`) in the project's instruction file sets effort for handed work using the harness's high, medium, or low terms without lowering any rule; if unsupported, say so once. Name the building and reviewing models in the handoff and PR. If a reviewer is unreachable, stop and report; anything else falls back here with one notice.
