# Conduct checklist — /flow-next:work

A correct run executes a spec or task end to end with all task state read and written through `flowctl`. One task (a one-task plan, a task-id run, or the direct route's implicit owner) is implemented inline by the conductor. Several tasks, or an explicit worker request, go through workers on the rolling or wave scheduler.

- [ ] Task state moves only through `flowctl start` and `flowctl done`, and completion is claimed only after `flowctl show <task-id> --json` reads `done`. Staging is `git add -- <changed files> .flow/`, never `git add -A`. A session that tracks tasks with TodoWrite or a plan file outside `.flow/` has broken this.
- [ ] No branch question is asked. Attended: the current branch when it is not the default branch, otherwise a new branch named for the spec's `branch_name`, stated in one line; the only setup question is the review question, and only when no review backend is configured. Autonomous: `--branch=new` named exactly `branch_name`, no questions. A branch question, or a review question with a backend configured, has broken this.
- [ ] Exactly one `Scheduling:` line prints before the first claim. One task with no implementer model or tier named, no `host` review mode, and room in context prints `Scheduling: inline (single task)`: the conductor claims, anchors, implements, commits, and runs `flowctl done` itself, with no worker spawned and `worker.md` not read. Otherwise the line is `rolling`, `wave (<reason>)`, or `degraded to wave (host lacks non-blocking dispatch)` per `multi-task.md`, and a single task sent to a worker names why in one line. A worker spawned for a plain single task, or a run with no `Scheduling:` line or two, has broken this.
- [ ] Tests are the focused tests for the code changed, with a failing test first where cheap. The full suite runs only when the repository's instructions or the user ask for it, once in Phase 4 and not again after later fixes; a command the instructions say to run when work is finished (a session-completion or definition-of-done checklist, or before committing, pushing or opening a PR) is such an ask and runs as written, while a command they only list is not. A `gate classify` exit 0 runs lint/format only, and each gate outcome surfaces as its own `Gates:` line. A full-suite run nobody asked for, a repeat after a fix, or `Gates: focused (full suite not requested)` when the instructions name such a finish command, has broken this.
- [ ] Review follows the risk rule: a change touching persisted or shared state, concurrency, security, data layout or migrations, or a multi-file feature, invokes `impl-review` on a green tree (attended: the result is handed back first and the review runs in the background, its verdict reported when it lands; unattended: the run waits), and `done` waits for SHIP. A small local change records `stage: impl-review - skipped(policy: risk - <reason>)`. Review is never deferred to a PR.
- [ ] A zero-task spec-id start fires the fork: interactive runs ask plan-first vs work-directly with a recommendation in `plan-vs-no-plan.md`'s shape; a `--no-plan` flag, stated intent, or the spec's own `no_plan: true` pre-answers it; autonomous runs without that instruction stop with `NEEDS_HUMAN: spec has no tasks - ...`; the direct route persists `spec set-no-plan` and mints exactly one implicit task (`satisfies` every spec R-ID, no `Touches:` line). A silent fall-through, an ask under autonomy, or a second mint has broken this.
- [ ] On the worker routes, every dispatch carries `FORBIDDEN` (the task's declared Touches) and a conductor-set `TIMEBOX`; a concurrent wave requires disjoint declared Touches and commits `.flow/` before creating workspaces; `PARALLEL_WAVE: true` workers never self-complete (the conductor integrates, reviews, and calls `done` on SHIP); progress is judged by side effects, and a task stops retrying after two consecutive non-`done` returns. A wave dispatched with missing or overlapping Touches, or a lane judged healthy on narration alone, has broken this.
- [ ] Completion review: a one-task spec whose review reached SHIP with every R-ID in `satisfies` persists `set-completion-review-status --status not_required --if-current unknown` and records the skip line; otherwise `spec-completion-review` runs. Work never writes a verdict status.
- [ ] The run closes with the final summary: `Tracker sync:` in one of its four states, one `Gates:` line per outcome, `Shipped: 0 (no PR yet ...)` for an all-done spec with no PR, and an executable `Next:` line. The spec is left open unless the user asked to close it. Discoveries outside the request are listed as follow-ups, as plain facts, with no offer to fold them in; no push or PR unless asked.
- [ ] A worker whose prompt carries `BASELINE_HANDOFF` checks that every path changed since the handoff's verified SHA is under `.flow/`; only then it records `baseline: green via handoff (...)` and skips the focused baseline commands (lint and format still run). Any other changed path runs the baseline normally. A handoff accepted over a changed source path has broken this.
- [ ] A task whose spec carries a `Design context` heading (`##` or `###`) makes the worker read the named `DESIGN.md` and use its tokens and patterns rather than hard-coded values; a missing `DESIGN.md` is noted and the work proceeds. Design context ignored because the heading was `###` has broken this.
