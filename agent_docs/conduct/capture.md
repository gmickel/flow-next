# Conduct checklist — /flow-next:capture

A correct interactive run saves a source-tagged spec after resolving material choices, shows its summary, and offers the saved file for editing.

- [ ] The body is materialized once and consumed by `spec set-plan --file`; interactive capture writes without an approve-and-write exchange. Autofix without `--yes` allocates nothing. An inferred tally never serves as evidence of user approval.
- [ ] Each saved spec has a compact summary and actual file path; a rewrite shows its diff. The editor offer opens saved files, re-reads user edits, and never restores the temporary body or mints a duplicate. A split choice gets no second body-ratification ask. Glossary/readiness consent stays separate; saving never starts implementation.
- [ ] Acceptance criteria capture newly authors carry `[user]` / `[paraphrase]` / `[inferred]` / `[strategy:<track>]` tags. Every `[user]`-tagged line is findable in `## Conversation Evidence`, and every evidence line quotes something the user actually typed — a fabricated `> user (turn N)` line (process formula, agent narration, tool output) fails the run even though findability passes over it; a close restatement is `[paraphrase]`. Process fences (new-vs-rewrite, ready-marking, "do not implement", Phase 0 duplicate-scan outcome) never appear in the spec body or `## Boundaries`, under any tag.
- [ ] Chart, B-ID, cluster, D-ID, and approved-asset evidence appears as links and references in the evidence sections without trailing source tags, and `flowctl chart link-spec` is called only after a successful create + set-plan.
- [ ] Refusal conditions fire rather than being worked around: an existing spec without `--rewrite`, a draft or stale briefing without a named-D-ID risk override, and a Ralph environment (`FLOW_RALPH` / `REVIEW_RECEIPT_PATH`) all stop the run.
- [ ] The commit stages only `.flow/specs/<id>.md`, its JSON sidecar, and `.flow/meta.json` when the counter moved. A run that reaches for `git add -A` has broken this.
- [ ] Phase 6 printed exactly one `Recommended next:` line per emitted footer block (base/rewrite: one total; split-as-proposed: one per created spec, judged per spec) above each `Next:` menu; no pipeline-variations rubric text was copied into the closer, and `chart` was never the recommended target.
- [ ] The `Recommended next:` judgment may name `/flow-next:work <SPEC_ID> --no-plan` for a ready cohesive spec, and `chart` stays outside the legal-target list. A closer that still claims a task must exist before `work` can run has broken this.
- [ ] The spec-level `no_plan` field is written only from the explicit `--no-plan` invocation flag (§5.9b), in interactive and autofix alike — never from conversation content, the draft's shape, or capture's own judgment; a set-time refusal (rewrite target with tasks) surfaces as a one-line notice, never a rollback. A capture that inferred no-plan has broken this.
