# Conduct checklist — /flow-next:work-rolling (experimental)

A correct run behaves exactly like canonical `/flow-next:work` everywhere except Phase 3, which it replaces with rolling per-task admission: admit at every worker-return event, isolated workspace per task, conductor-owned review, shared notes surface. Canonical work's own checklist (`work.md`) applies in full to the consumed-by-pointer surfaces; the items below cover only the rolling delta.

- [ ] The canonical `flow-next-work` files are consumed by pointer and stay byte-unchanged — the transcript reads `$WORK_SKILL/SKILL.md`, `$WORK_SKILL/phases.md`, and `$WORK_SKILL/references/wave-join.md` rather than restating them, and `git diff` shows no edit under `skills/flow-next-work/`. A run that forked or patched a canonical file has broken this.
- [ ] Every admission event prints the rolling report block — the canonical lines plus `In-flight:`, `Admitted:`, and `Held:` (each held task with its reason) — and admission is recomputed after each event (worker return or review completion), never precomputed for the run and never deferred to the end of a task's review tail. A candidate missing a `**Touches:**` declaration, intersecting an in-flight task, or dep-connected to one is held, and an empty admissible set with a non-empty frontier reports a `Sequential fallback:` reason.
- [ ] With `planSync.enabled=true` the run dispatches strictly serially (at most one in-flight task) and reports `Sequential fallback: planSync.enabled=true` once; canonical 3e then runs after each completed task. A concurrent admission under an enabled plan-sync has broken this.
- [ ] Every dispatched worker — including a one-task admission — carries `PARALLEL_WAVE: true` and returns the parallel handover; the conductor integrates that task (wave-join evidence + SHA normalization), runs its review itself, and calls `flowctl done` only on SHIP. A worker that self-completed, self-reviewed, or a join conflict resolved by hand instead of one serial retry has broken this.
- [ ] The notes directory is created at Phase 3 start under the state-dir sibling, keyed by spec id + run identifier; its path (never its content) rides every worker and scout dispatch prompt; it is deleted only after canonical Phase 5 completes cleanly (never at quiesce - a quality/ship failure still needs the notes). A creation failure degrades to `Notes surface: unavailable (...)` and the run continues.
- [ ] Cross-run claim contention fails closed (verified once, 2026-08-22, in an isolated `FLOW_STATE_DIR` sandbox: `flowctl start` on a task claimed by another actor returns rc 1 `claimed by '<actor>'`; a same-actor re-start is flowctl's own-task resume, so admission additionally skips any task already `in_progress`). The loser drops the task rather than clearing the claim; a run that used `--force`/`--reclaim` to take another run's task has broken this.
