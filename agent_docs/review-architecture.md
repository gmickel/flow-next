# Review command architecture

Maintainer notes on how `flowctl`'s review commands are built. Moved from the shipped
`plugins/flow-next/docs/flowctl.md`, which keeps only the user-facing behaviour (see its
[Review commands](../plugins/flow-next/docs/flowctl.md#review-commands) section).

All twelve `flowctl {codex,copilot,cursor,claude} {impl,plan,completion}-review` commands are thin wrappers over one driver: `cmd_backend_review(backend, kind)`. Per-backend variance (sandbox flags, session markers, argv-budget fit or stdin delivery, receipt shape) lives as hooks on `BACKEND_REGISTRY` entries, wired lazily by `_wire_backend_review_hooks`. Adding a review backend is a registry entry (hooks + models/efforts), not a new clone of the pipeline. The first-round fan-out (`flowctl <backend> impl-review-fanout` and `impl-review-fanout-finalize`) is one runner registered under every CLI backend, with no per-backend gating.

Adding or removing a backend is still an enumeration sweep beyond the registry entry. Check per-backend special cases inside shared helpers (`backend == "<name>"` branches and maps such as `strict_grammar` in `_resolve_session_pass_spec`), which a grep for backend tuples never lists; regenerate the config schema with `scripts/gen_flow_config_schema.py`; and grep prose lists in `plugins/flow-next/{skills,agents,docs}` in every shape (backticked, comma, slash and pipe lists; skip `codex/`, which the sync regenerates). Read every hit: what remains must be a per-backend case arm or section header. Run `python3 scripts/gen_tracker_manifest.py` after the last `flowctl.py` edit, not before a review fix.

The output slot of a backend's exec result is the verdict channel. `_finish_backend_exec` parses the verdict before it looks at the exit code, so a failure never puts envelope text in that slot: it returns empty output and sends diagnostics to stderr. A new headless backend pins its CLI's exact success shape rather than reusing another backend's lenient parser (`_parse_claude_result` accepts exactly one JSON object with `type == "result"`), and its regressions run through `_finish_backend_exec`, not only through the runner.

R-ID coverage has two gates. A non-deferred `not-addressed` R-ID forces NEEDS_WORK, and SHIP needs every R-ID `met` or `deferred`; so `partial` passes the coverage gate but blocks SHIP, while `deferred` passes both. A route that promises an honest "completed but not met" outcome names `deferred` and traces it through review, `done` and unattended make-pr; step 5 of [hill-climb.md](../plugins/flow-next/skills/flow-next-work/references/hill-climb.md) is the pattern.

Reviewer tallies prefer one fenced `json` block (`suppressed_count`, `classification_counts`, `unaddressed`, `deep_findings`); prose tally lines remain a logged fallback. The `<verdict>SHIP|NEEDS_WORK|MAJOR_RETHINK</verdict>` tag contract is unchanged. Plan/completion handlers self-write `*_review_status` from the verdict; the standalone `spec set-*-review-status` commands still work.
