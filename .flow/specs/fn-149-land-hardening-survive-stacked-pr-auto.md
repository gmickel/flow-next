## Goal & Context

Land babysits build-loop PRs one merge frontier at a time: gates anchored to the head SHA and the last push, a merge guarded by `--match-head-commit`, branch deletion on merge, and a post-merge tail. Those assumptions break on a chain of dependent PRs, and the break is not graceful. Verified on 2026-08-27 in this repo: squash-merging the base PR with branch deletion closed the dependent PR permanently, and recovery took a hand rebase, a force-push, and a successor PR. Verified on 2026-07-31 and re-verified on 2026-09-13 against GitHub: the legacy merge endpoint refuses any PR that is in a GitHub stack, the stack merge endpoint merges every unmerged layer below the one requested, and after a bottom merge GitHub rewrites the heads of the layers above, which every SHA-anchored gate reads as either reviewer activity or a violated head match.

This spec makes land correct on chains and stacks, with one rule set that covers both shapes the companion authoring spec (fn-152) produces: a plain chain on any host, and a GitHub stack when the link succeeded. Land merges only the frontier, keeps a review verdict across a rebase when the patch did not change, retargets the next layer itself when the host did not, never deletes a branch a child still targets, and reports the chain's state in every verdict. A PR that is neither chained nor stacked keeps byte-identical behaviour.

Who benefits: a person who reviews a chain and wants land to drain it without a hand rebase per layer, and anyone whose flow-authored PR gets stacked by a human or another tool, since land must not break or collapse a stack it did not build.

## Vocabulary

Shared with fn-152: **chain** (dependent PR whose base is the parent's branch, any host), **stack** (GitHub's server-side object over a chain), **layer**, **frontier** (the bottom open layer). Added here:

- **Native path** is the merge and retarget path when the PR's REST payload carries a non-null `stack` object. GitHub owns sequential merge and auto-retarget.
- **Plain path** is the path when `stack` is null and the PR's base is not the chain's base branch. Land owns retarget.
- **Verdict SHA** is the head SHA a merge verdict or review gate was evaluated at. **Verdict patch-id** is the stable `git patch-id` of the base-to-head diff at that SHA.
- **Contiguous verified run** is the set of layers from the frontier upward whose gates are green at their current patch. Land merges at most one layer per tick and reports the run's ceiling.

## Architecture & Data Models

**Shape detection per PR, every tick.** Land adds one `gh api repos/{owner}/{repo}/pulls/<n>` read beside the existing `gh pr view` probe and classifies the PR:

| `stack` object | base ref | Shape | Merge path | Retarget owner |
|---|---|---|---|---|
| non-null | any | stacked layer | native (merge-async) | GitHub |
| null | not the chain base | plain chain layer | existing `gh pr merge` | land |
| null | chain base (default branch or human-chosen base) | standalone | existing `gh pr merge` | none |

**Children are detected independently of shape.** Before any merge, land reads `gh pr list --base <head branch> --state open`; a non-empty result means the PR has open children, on every shape including standalone (the bottom layer of a plain chain is standalone by this table and has a child). Open children decide branch deletion (below); shape decides only the merge endpoint and who retargets.

The chain base is the base ref recorded in make-pr's footer marker for the bottom layer, or the default branch when no marker names another. The classification is re-derived from the PR on every tick, logged in the tick output, and carried in the verdict reason; it is never stored in the ledger and never read from config, because a human can stack, unstack, or retarget by hand between ticks and only the PR tells the truth.

**Frontier rule.** A stacked layer merges only when it is the lowest open PR in `GET /repos/{owner}/{repo}/stacks/{stack_number}`. A plain chain layer merges only when its base is the chain base, which after the parent merges means land has retargeted it. Land already holds a merge until every `depends_on_epics` spec is `done`; that check stays and is the same rule expressed through flow state. Both checks must pass; a stack a human built without flow dependency edges is covered by the stack read alone.

**Verdict carry-over by patch-id.** The ledger holds one evidence binding per PR, `(verdict_head, verdict_base, verdict_patch_id, verdict_window_anchor)`, written only when the review gates were satisfied at that head (a head-current review, a clean-review comment naming that head, or a green merge verdict). An unsatisfied evaluation never writes it. On every tick land computes the current patch-id of base-to-head. Equal to `verdict_patch_id` means the code the reviewer judged is unchanged: every review gate is evaluated against `verdict_head` instead of the current head, so a comment that names the original head keeps satisfying across any number of equivalent head moves and ordinary ticks, and only CI, mergeability, and dependency contiguity are re-read at the current head. A different patch-id clears the binding, and the gates run against the current head until they are satisfied there, which writes a new binding. This is the mechanism that lets a server-side rebase, land's own retarget, or a human rebase move the head without either laundering a stale approval or forcing a fresh review of an unchanged diff.

**Single topology writer, and the chain invariant it keeps.** Only land, inside its tick claim, retargets or rebases a chained branch. Work and make-pr never rewrite a branch that has a PR (make-pr's merged-parent rebase in fn-152 runs before a PR exists). Resolve-pr and the ci-fix step push commits, never rewrites. The invariant land maintains across every rewrite is: **every open layer's history contains the current tip of the layer below it.** That is what makes `git merge-base <child> <parent tip>` the exact boundary of the parent's work inside the child, and it is why a rewrite of one layer must cascade upward in the same operation. Rewriting B alone and leaving C on B's old history would break the invariant, and the next boundary computation for C would resolve below A and replay merged commits. Humans may still rebase by hand; the patch-id rule absorbs the head move, and a hand rebase that breaks the invariant surfaces as a conflict or as a boundary land refuses to trust (below).

**Branch janitor.** The merge call drops `--delete-branch` whenever the PR has open children. The branch name is recorded in a top-level `pending_branch_deletes` map in the ledger, keyed by branch and holding the merged PR number, which survives the successful-tail cleanup of the PR's own entry and is not tied to spec discovery. Every tick, before candidate selection and whether or not any open spec exists, land sweeps that map: a branch with no open PR targeting it is deleted and removed from the map; a branch that still has children stays and is reported. On the native path GitHub's retarget clears the children quickly; on the plain path land's own retarget does. Deleting first would close the child (the 2026-08-27 failure).

**Ledger additions (exhaustive).** Only what must survive between ticks is stored. Per PR URL: `verdict_head`, `verdict_base`, `verdict_patch_id`, `verdict_window_anchor` (the patience anchor in force when the binding was written), and `merge_async_uuid` with `merge_async_expected_head` (present only while a submit is pending). At the ledger's top level, beside the PR entries: `pending_branch_deletes`, a map of branch name to `{"pr": <number>, "merged_at": "<iso8601>"}`, which the per-PR tail cleanup never touches; and `cascade`, present only while a chain rewrite is between its first push and its last base edit, with the exhaustive shape `{"chain_base": "<ref>", "merged_parent": "<branch>", "layers": [{"branch": "<b>", "pr": <number>, "old_tip": "<sha>", "new_tip": "<sha>", "published": false, "base_edited": false}]}` (`base_edited` meaningful on the first layer only). Shape, stack number, position, chain base, and any retarget SHA are re-derived from the PR and git each tick and never stored. All fields are skill-owned scratch in the existing ledger file, written by the existing atomic jq-plus-mv idiom. No flowctl plumbing.

## API Contracts

### Native merge (stacked layer, frontier, all gates green)

```bash
gh api --method PUT "repos/{owner}/{repo}/pulls/<n>/merge-async" \
  -f merge_method=squash -f merge_action=direct_merge -f sha="$HEAD_OID"
```

- Response 202 with `status: pending` and `details.uuid`, `details.expected_head_sha`: land records both in the ledger. `expected_head_sha` must equal `$HEAD_OID`; a mismatch is `BLOCKED` with the two SHAs named, since the endpoint would merge a head the gates never judged. Land then polls `GET .../merge-async/<uuid>` until `status` is `merged` or `failed`, within the same bounded budget the merge-verdict command uses (600 seconds). `pending` past the budget is reported as `RESOLVING` and re-polled next tick from the stored uuid; land never re-submits while a uuid is pending, and clears the uuid on any terminal status. The result is retained by GitHub for 24 hours; a 404 on the stored uuid is treated as unknown and the PR is re-probed for `state == MERGED` before any new submit.
- Response 200 means already merged or already queued; land re-probes the PR and proceeds as merged only on `state == MERGED` with a non-null `mergedAt`.
- Response 400 (not mergeable, closed, or draft) is `BLOCKED` with the message. Land flips a draft ready before submitting, exactly as it does before the legacy merge.
- Response 409 (a merge request already enqueued) is `RESOLVING`; the next tick polls whatever uuid the ledger holds, or re-probes the PR when it holds none.
- `merge_action` is always `direct_merge`; `merge_queue` stays forbidden.
- The `sha` head pin is enforced server-side, proven live on 2026-09-13 (research section): a stale `sha` returns HTTP 400 with `{"status":"failed","details":{"message":"Pull request head branch was modified."}}` and nothing merges, including on a layer whose head GitHub itself moved by auto-retarget. Land therefore always sends `sha`, and the `expected_head_sha` echo is a consistency check, never the guard. The R16 fixture keeps a stale-pin regression so a future API change surfaces as a failing test; if that fixture ever observes a merge despite a stale pin, native submission is disabled with `NEEDS_HUMAN: merge-async does not enforce a head pin; merge #<n> from the stack UI`. There is no fallback to response-only validation.
- `FLOW_PR_MERGE_CMD`: the override wraps the legacy merge command and cannot express the asynchronous endpoint. When the override is set and the PR is stacked, land reports `NEEDS_HUMAN: FLOW_PR_MERGE_CMD is set but #<n> is a stacked layer; stacked merges use the merge-async endpoint` and merges nothing.
- A stacked layer that is not the lowest open layer never reaches this call; the verdict is `AWAITING_REVIEW` with reason `stack #<s> layer <p> of <size> awaits <k> lower layer(s)`.

### Plain chain merge and retarget

- Frontier check: the PR's base equals the chain base, and every dependency spec is `done`. Otherwise `AWAITING_REVIEW` with reason `chain layer awaits parent #<n>`.
- Merge: the existing `gh pr merge <n> --squash --match-head-commit <sha>` call, with `--delete-branch` present only when the PR has no open children (the shape-independent check above). The override contract for `FLOW_PR_MERGE_CMD` is unchanged in argument order; the delete flag is simply omitted from the argument list when children exist, and the branch is added to `pending_branch_deletes`.
- Retarget of the chain above a merged layer, on the tick after the parent PR shows `state == MERGED`, when the next layer's base is still the merged parent's branch. The rewrite cascades over every open layer above the merged one, bottom-up, and is split into two phases so that a failure in the second can always be resumed: **prepare** every layer locally, then **publish**.

  Prepare (no remote writes):

```bash
git fetch origin "<chain_base>" "<merged_parent_branch>" <every open layer branch above it>
ONTO="origin/<chain_base>"; BELOW_OLD="origin/<merged_parent_branch>"
for LAYER in <open layers, bottom-up>; do
  OLD_TIP=$(git rev-parse "origin/$LAYER")
  FORK=$(git merge-base "$OLD_TIP" "$BELOW_OLD")             # boundary against the PRE-rewrite tip of the layer below
  git merge-base --is-ancestor "$FORK" "origin/<chain_base>" && { echo "boundary for $LAYER is on the chain base; refusing"; exit 1; }
  # in a temporary worktree of $OLD_TIP:
  git rebase --onto "$ONTO" "$FORK"
  NEW_TIP=$(git rev-parse HEAD)
  git update-ref "refs/flow-next/cascade/$LAYER" "$NEW_TIP"   # local ref, keeps the rewrite reachable across ticks
  ONTO="$NEW_TIP"; BELOW_OLD="$OLD_TIP"
done
```

  Before the first push, land writes a cascade record to the ledger (shape below) listing, per layer bottom-up, `branch`, `old_tip`, `new_tip`, `published: false`, and for the first layer `base_edited: false`. Publish then walks the record bottom-up: `ls-remote` must equal `old_tip`, push `refs/flow-next/cascade/<layer>` to `refs/heads/<layer>` with `--force-with-lease=<layer>:<old_tip>`, mark `published: true`; for the first layer only, `gh pr edit --base <chain_base>` and mark `base_edited: true`. When every layer is published and the base edit is done, the record is removed and the local cascade refs deleted.

  Resume: a tick that finds a cascade record does nothing else for that chain until the record clears. It re-reads each unpublished layer's remote head and reconciles it against the record before deciding anything, because a push can succeed while the ledger write after it is lost. Four cases, tested in this order: remote equals `new_tip`, or `new_tip` is an ancestor of the remote head (the push landed, and possibly someone committed on top), means the layer is already published: mark it `published: true`, perform no rewrite, and carry on to its base edit if pending. Remote equals `old_tip` means the prepared `new_tip` is still valid and is pushed. `old_tip` is an ancestor of the remote head (someone committed on the old history) means the layer is re-prepared from its current remote head with `FORK = merge-base(<current head>, <recorded old_tip of the layer below>)` and `ONTO = <recorded new_tip of the layer below>`, which is exactly the prepare step with recorded SHAs in place of live reads, and every layer above it is re-prepared the same way. Anything else (the remote head is related to neither recorded tip) is `NEEDS_HUMAN: <layer> was rewritten by someone else during a cascade; reconcile by hand`. A published layer whose base edit failed gets the base edit retried. Resumption therefore never rewrites a layer that already carries its rewrite. The recorded old tips are what make this possible: after a force-push the old history is reachable only through the record and the objects in this clone, which is why land already runs from one clone per ledger. A record whose local cascade refs or old-tip objects are missing (a different clone) is `NEEDS_HUMAN: cascade for <chain> was prepared in another checkout; finish it there or rebase by hand`.

  The merged parent branch must still exist for the first boundary to resolve, which the branch janitor guarantees. A boundary that resolves onto the chain base means the invariant was already broken (a hand rewrite below), and land refuses the whole cascade before any push with `NEEDS_HUMAN: chain history for <layer> does not contain its parent; rebase by hand`. A rebase conflict during prepare aborts that layer, removes the worktree, writes no record, and reports `BLOCKED: retarget of #<n> onto <its new base> conflicts in <files>`; nothing has been published, so the chain is exactly as before; land never hand-resolves a conflict, matching the existing catch-up rule. A lease failure during publish leaves the record in place and reports `RESOLVING`; the next tick resumes as above, so a transient race never strands the chain. After each layer's publication the next gate evaluation computes that layer's patch-id against its new base, and the verdict carry-over rule decides whether the review gates stay satisfied.
- This is the only force-push land may perform. It is bounded to: the open layers of a chain it is babysitting, each with a lease on the exact tip it read, inside the tick claim, after the layer below merged. The general no-force-push rule stays in place for every other step and in the Forbidden list.

### Patch-id computation

```bash
git diff "origin/<base>...<head>" | git patch-id --stable | cut -d' ' -f1
```

Computed from fetched refs, never from a working-tree checkout of the PR, on every tick. The evidence binding is written only when the review gates are satisfied at a head, and it is never overwritten by an unsatisfied evaluation or by an equivalent head move. While the current patch-id equals `verdict_patch_id`, the head-current automated review conjunct, the clean-review comment's head-prefix conjunct, and the stale-approval detector's `land_pushed_sha` comparison are all evaluated against `verdict_head`, on this tick and every later tick, through any number of equivalent rebases, until the patch changes. The merge-verdict command (`land.mergeVerdictCommand`) is not carried: it re-runs at the current head on every merge attempt, because carrying a verdict command's result from review evidence would let review evidence stand in for a gate the repository chose to run itself. CI checks, `mergeStateStatus`, and the dependency contiguity check are likewise always re-read at the current head. A different patch-id clears the binding and every carried conjunct, and the gates run against the current head from scratch; a patch-id that cannot be computed (fetch failure) is treated as different.

### Patience window on a server-side head move

One rule, applied by the agent at the gate: a head move with an unchanged patch-id is not a push. The patience window keeps the anchor recorded with the verdict (`verdict_window_anchor`) instead of re-anchoring to the move, so a retarget by GitHub, by land, or by a human rebase never restarts the reviewer wait or holds a layer in `AWAITING_REVIEW` without bound. A head move with a different patch-id is a push and re-anchors as today.

### Discovery and verdicts

- Land's spec selection is unchanged (open specs with all tasks done, or the one scoped id). The chain shape is discovered from the PR, not from the spec.
- A stacked layer's `LAND_VERDICT` reason ends with `; stack #<s> layer <p> of <size>`; a plain chain layer's ends with `; chain on #<parent_n>`; a standalone PR's reason is byte-identical to today. When land holds a layer for lower layers, the reason names the frontier PR number and how many layers separate them, so a driver transcript shows the ceiling.
- After any merge in a chain or stack, the remaining planned merges in the same tick downgrade to `RESOLVING` (the existing sibling re-gate rule); the next layer is re-read next tick.
- `autoMergeRequest` and `mergeStateStatus` are never read as stack readiness. Advancement to the next layer happens only after the merged layer's re-probe shows `state == MERGED` with a non-null `mergedAt`.

### Tail

- Spec close, release-follow, the tracker touchpoint, and persist run per merged layer as today, and the successful tail still deletes the PR's own ledger entry. The `pending_branch_deletes` map is outside that entry and survives it. The janitor sweep runs at the start of every tick, before candidate selection and independent of whether any open spec exists, over every branch in the map: a branch with no open PR targeting it is deleted with `gh api --method DELETE repos/{owner}/{repo}/git/refs/heads/<branch>` and removed from the map; a 422 (already gone) removes it silently; a 403 is reported once per tick and the entry kept. A merge, spec close, child retarget in a later tick, and deletion in a tick after that therefore compose across separate invocations.
- Release batching across a chain is out of scope; a repo that wants one release per chain runs land with `land.release` off and releases by hand after the last layer, which is how this pair of specs ships.

## Edge Cases & Constraints

- **Stack collapse hazard.** merge-async on a non-frontier layer merges every open layer below it. The frontier rule is the only guard; land reads the stack object on every tick, never from the ledger, and the merge submit reads the stack once more within the same tick immediately before submitting. Two reads bound the window to seconds.
- **Human merged the frontier from the stack UI between ticks.** The next tick sees the stack with one fewer open layer and the new frontier's head moved by GitHub's rebase; the patch-id rule carries the verdict, CI re-runs, and land proceeds. This is the default consumption model and must need nothing from land beyond re-reading.
- **Human unstacked the chain.** The `stack` object becomes null and the PR's base is still the parent branch: the plain path takes over on the next tick with no ledger migration; `stack_number` and `stack_position` are cleared.
- **Human stacked a flow PR by hand** (`gh stack link` or the UI). The native path applies; flow dependency edges may be absent, so the stack read alone gates the frontier.
- **Parent closed unmerged** while the child is open. The child is `NEEDS_HUMAN: chain broken; parent #<n> closed unmerged`, never retargeted automatically, because the child's commits include the parent's work and a human must decide whether the parent's change lives on in the child.
- **Parent branch already deleted** when the child needs a plain retarget (a human deleted it). If the child is still open, `FORK` is computed from the child's PR base SHA recorded by GitHub (`base.sha` in the REST payload at the last tick, stored as part of `verdict_base`), and the rebase proceeds; if that is unavailable, `NEEDS_HUMAN: parent branch <b> gone; rebase #<n> onto <chain_base> by hand`. If GitHub already closed the child, `NEEDS_HUMAN` names the successor-PR recovery.
- **Retarget conflict.** `BLOCKED` with the files named, like any conflict today. The layer above it stays `AWAITING_REVIEW`; the chain's ceiling is reported in the verdict.
- **Two land ticks.** The tick lock already serialises land per clone; the force-with-lease adds a second guard for a rebase raced by another actor.
- **Preview drift.** The stacks API is public preview. Any non-2xx from a stack read that is not a clean 404 degrades to the plain-path classification for that tick with one stderr line; a stack read 404 on a PR whose payload still carries a `stack` object is `NEEDS_HUMAN` naming the inconsistency rather than a guess.
- **App permissions.** Deferred branch deletion needs the same branch-delete permission `--delete-branch` needed; a 403 is reported once and the ledger entry kept for a later tick, never a strike.
- **Byte-identical standalone path.** A PR with `stack` null and base equal to the chain base runs today's gate tree, merge call with `--delete-branch`, and tail with identical verdicts and ledger writes, plus the new ledger fields written as `standalone` and the extra REST read.
- **The retarget force-push is attributed to land's own account.** GitHub records `head_ref_force_pushed` on the upper layer under the account that submitted the merge. Land must not read that event as its own authored push: `land_pushed_sha` is written only by land's ci-fix, catch-up, and cascade pushes, so the R8 rule (unchanged patch-id means not a push) decides, never the actor.
- **A stale pin on a stacked frontier is a normal `RESOLVING`.** Between land's head read and its submit, GitHub can move a layer's head (a lower layer merged from the UI). The 400 refusal is the intended outcome; land re-reads the head, re-applies the patch-id rule, and submits again next tick.

## Acceptance Criteria

- **R1:** Every tick classifies each babysat PR as stacked, plain chain, or standalone from the REST payload's `stack` object and its base ref, logs the shape, and stores nothing about it. Errors: a failed REST read degrades to the plain-path classification with one stderr line; a `stack` object whose stack read returns 404 is `NEEDS_HUMAN` naming the inconsistency.
- **R2:** A stacked layer merges only when it is the lowest open layer of its stack read in the same tick, immediately before submit; any other layer is `AWAITING_REVIEW` naming the frontier and the count of lower layers. Errors: none beyond R1's read failures.
- **R3:** A stacked frontier with all gates green merges via `merge-async` with squash, direct merge, and the client head pin, which is enforced server-side (proven 2026-09-13, kept as an R16 regression); land verifies the echoed expected head, polls the uuid within the bounded budget, and advances only on `merged`. Errors: a stale pin is refused with 400 and `failed` before anything merges, which land reports as `RESOLVING` and re-reads the head next tick; a regression that observes a merge despite a stale pin disables native submission with `NEEDS_HUMAN` and no fallback; expected-head mismatch is `BLOCKED` naming both SHAs; `failed` is `BLOCKED` with the message; `pending` past budget is `RESOLVING` and re-polled from the stored uuid, never re-submitted; 400 is `BLOCKED`; 409 is `RESOLVING`; a set `FLOW_PR_MERGE_CMD` on a stacked layer is `NEEDS_HUMAN` with nothing merged.
- **R4:** A plain chain layer merges only when its base is the chain base and every dependency spec is done, through the existing merge call and head guard. Errors: base still a parent branch is `AWAITING_REVIEW` naming the parent PR; the existing head-mismatch and refusal classifications are unchanged.
- **R5:** On every shape, a PR with open children (an open PR whose base is this PR's head branch) merges without `--delete-branch` and its branch is recorded in the top-level `pending_branch_deletes` map, which the per-PR tail cleanup never removes; a sweep at the start of every tick, independent of spec discovery, deletes each recorded branch once no open PR targets it. Errors: 403 on deletion is reported once per tick and the entry kept, never a strike; 422 (already gone) removes the entry silently. A PR with no open children is deleted at merge exactly as today.
- **R6:** After a layer merges, every open plain chain layer above it is rewritten bottom-up in one cascade with two phases. Prepare rebases every layer locally, each from its merge-base with the pre-rewrite tip of the layer below onto the rewritten tip below it (the chain base for the first), and keeps each result under a local cascade ref. Publish records the per-layer old and new tips in the ledger before the first push, force-pushes each layer with a lease on its recorded old tip, retargets only the first layer with `gh pr edit --base`, and clears the record after the last base edit. A tick that finds a record resumes it by reconciling each unpublished layer's remote head against the recorded tips first: a head at or above `new_tip` is marked published without a second rewrite, a head at `old_tip` is pushed as prepared, a head above `old_tip` is re-prepared from its current head against the recorded tips, and a missed base edit is retried. Errors: a head related to neither recorded tip is `NEEDS_HUMAN` naming the layer; a boundary on the chain base refuses before any push as `NEEDS_HUMAN` naming the layer; a rebase conflict during prepare is `BLOCKED` naming the files with nothing published; a lease failure during publish is `RESOLVING` with the record kept, never a stranded chain; a record whose objects live in another clone is `NEEDS_HUMAN`; a missing parent branch falls back to the recorded base SHA or is `NEEDS_HUMAN`; a closed parent is `NEEDS_HUMAN: chain broken`. No other step in land may force-push; the Forbidden list says so.
- **R7:** The ledger holds one evidence binding per PR (verdict head, base, stable patch-id, window anchor), written only when the review gates were satisfied at that head and never by an unsatisfied evaluation or an equivalent head move. While the current patch-id equals the bound one, the review gates and the stale-approval comparison are evaluated against the bound head on this and every later tick, through repeated equivalent rebases, while the merge-verdict command, CI, mergeability, and dependency contiguity are always re-run at the current head. Errors: a different patch-id clears the binding and re-gates from scratch; a patch-id that cannot be computed (fetch failure) is treated as different.
- **R8:** A head move with an equal patch-id is not a push: the reviewer patience window keeps the anchor recorded with the verdict, so a retarget never restarts the wait or holds a layer in `AWAITING_REVIEW` without bound. Errors: none beyond R7.
- **R9:** Land never merges more than one layer of a chain or stack per tick; after a merge, remaining planned merges downgrade to `RESOLVING`, and advancement to the next layer requires the merged layer's re-probe to show `state == MERGED` with a non-null `mergedAt`. `autoMergeRequest` and `mergeStateStatus` are never read as stack readiness. No error surface beyond the existing re-probe failure, which is `NEEDS_HUMAN`.
- **R10:** The `LAND_VERDICT` reason names the stack number, layer position, and size for a stacked layer, the parent PR for a plain chain layer, and the frontier plus separating layer count when a layer is held; standalone PRs print byte-identical verdicts. No error surface.
- **R11:** A standalone PR (null `stack`, base equal to the chain base) with no open children keeps identical gate verdicts, merge arguments including `--delete-branch`, tail order, and ledger writes for every field that exists today; the only additions are the extra REST read, the children probe, and the evidence binding. A standalone PR with open children is the bottom of a plain chain and follows R5. No error surface.
- **R12:** `merge_action` is always `direct_merge`; no merge-queue enrolment and no auto-merge arming on any path. No error surface.
- **R13:** No configuration key is added or read; `get_default_config()`, the generated schema, and the drift test are unchanged. No flowctl Python changes. No error surface.
- **R14:** Documentation: the land skill reference gains a chains-and-stacks section covering the three shapes, the frontier rule, the collapse hazard, merge-async, patch-id carry-over, the one bounded force-push, and the branch janitor; the orchestration page's landing section and the troubleshooting page (chain broken, retarget conflict, pending merge-async) are updated; the changelog carries the entry under Unreleased alongside fn-152's. No error surface.
- **R15:** Machinery is bounded to hazards the agent cannot observe: the second stack read before submit (collapse), the leased force-push (a raced rebase), the deferred branch deletion with its top-level pending map (a closed child), the prepare-then-publish cascade with its resumable record (a replayed merged commit, a stranded chain after a lost lease), and the stored evidence binding plus pending uuid (state that does not survive a tick). Every other decision in this spec is a rule the agent applies from the PR and git each tick; no new lock, poller, config key, or derived-state file is introduced. No error surface.
- **R16:** Verification uses disposable git fixtures with a bare origin and a stubbed `gh`, and covers at minimum: one fixture per shape; a three-layer plain chain A, B, C with a multi-commit squash-merged A and then B, asserting C's boundary and diff after each cascade; the same chain where B publishes and C's leased push fails, with a later invocation completing the cascade from the record without manual rebasing, plus the variant where C moved in between and is re-prepared, and the variant where the process stops between a successful push and the ledger write, asserting that resumption performs no second rewrite; merge, spec close, child retarget, and deletion across four separate ticks; consecutive ticks and repeated equivalent rebases with a single clean-review comment naming the original head and no new review; a stale `sha` refused by the merge-async stub and the disabled-submission path; and the standalone-with-children case merging without deletion. Tests pin behaviour and shapes, never prose (the repo's G2 rule). No error surface.

## Boundaries

- No chain authoring: selection, branch-from-parent, base cascade, and stack linking are fn-152.
- No stack restructuring, no unstack, no reorder; land reads stacks and merges frontiers only.
- No merge-queue integration; `direct_merge` only.
- No gh-stack extension dependency; every call is `gh api` or `gh pr`.
- No force-push beyond the single bounded retarget in R6.
- No hand conflict resolution; a conflicting retarget is `BLOCKED`.
- No release batching across a chain.
- No flowctl changes; gates, reads, the merge-async loop, the patch-id computation, and the retarget are land skill prose plus `gh` and `git` fences, like the existing merge block.
- No GitLab merge-request chains; the plain path is shaped so fn-73 can inherit it, and nothing more.

## Decision Context

### Motivation

The July version of this spec assumed the GitHub stack API was the only mechanism and that land could never rebase. Two things changed. The 2026-08-27 incident showed that a chain without native stacking is what land will meet in the wild, and that the failure mode is total: a closed child, a hand rebase, a successor PR, and orphaned evidence SHAs. A survey of an established autonomous stacking playbook showed the durable rules for chains on any forge: verdicts keyed to the patch rather than the SHA, one topology writer, land only the contiguous verified run from the bottom, advance only on a confirmed merge, and never trust an auto-merge flag as readiness. Those rules are this spec's R6 through R9. The native API then becomes the cheaper path on GitHub, where the server does the rebase and retarget, and re-verification on 2026-09-13 found that merge-async now accepts a client head pin, which removes the July objection that the endpoint could merge a head the gates never saw.

### Implementation Tradeoffs

- **Patch-id carry-over over full re-gate.** A full re-gate after every server-side rebase would force a fresh human review of an unchanged diff on every layer above every merge, which makes stacks slower than serial PRs. Patch-id equality is the exact test for "the reviewed code did not change". CI still re-runs because the base did change.
- **Land owns the plain retarget.** The alternative, refusing and reporting `NEEDS_HUMAN` on every parent merge, is what the repo lives with today and what the 2026-08-27 incident cost. A bounded, leased force-push inside the tick claim, with conflicts still refused, is the smallest mechanism that makes chains work off GitHub's preview.
- **Branch janitor over never deleting.** Leaving branches forever changes the repo's hygiene for every user; deleting immediately closes children. Deferred deletion keeps today's end state.
- **Two reads of the stack per tick.** The collapse hazard is severe and the read is cheap; reading once more immediately before submit bounds the window without a lock the API does not offer.
- **Shape from the PR, never from the ledger or a config key.** A human can stack, unstack, or retarget by hand between ticks; only the PR tells the truth.
- **Dogfooding order.** This spec ships first. fn-152's PR is then built as a chain layer on this spec's branch, which is the first live chain land meets; landing the pair is done from the stack UI or with the released land, because skills run the installed plugin, not the working tree. Both specs ship in one release; the release tail runs once after the second merge.

## Resolved via Research

Written by the flow conductor's research pass on 2026-09-13; live probes and GitHub docs, no scouts.

- `PUT /repos/{owner}/{repo}/pulls/{n}/merge-async` accepts `commit_title`, `commit_message`, `sha` ("SHA that pull request head must match to allow merge"), `merge_method` (`merge|squash|rebase`), `merge_action` (`default|direct_merge|merge_queue`); returns 202 with `status: pending` plus `details.uuid` and `details.expected_head_sha`, 200 when already merged or queued, 400 when not ready, 409 when a request is already enqueued; `GET .../merge-async/{uuid}` returns the same schema, retained 24 hours. "When using this endpoint to merge a stacked pull request, all pull requests in the stack up to and including the requested PR will be merged"; it is the required method for stacked PRs and also works on unstacked ones. Source: https://docs.github.com/en/rest/pulls/pulls
- "Merging a stacked pull request requires the asynchronous merge API. The legacy pull request merge endpoints can't merge a stack." Source: https://docs.github.com/en/pull-requests/tutorials/roll-out-stacked-prs
- After a bottom merge "the pull requests above stay open and automatically re-target the stack's base branch" and "the remaining branches are automatically rebased"; merge requirements for every layer are determined by the bottom PR's base branch; public preview, subject to change. Source: https://docs.github.com/en/pull-requests/get-started/about-stacked-prs
- Stack read endpoints and the `stack` object on the PR payload: see fn-152's research section. Live on 2026-09-13 the July stack in the smoke repository reads back unchanged. Source: `gh api repos/gmickel/stacks-api-smoke/stacks`
- Branch deletion, not the squash, closed the dependent PR on 2026-08-27; a plain dependent PR whose parent merged without deletion stayed open for a month in the smoke repository. Sources: `.flow/memory/knowledge/workflow/stacked-pr-squash-close-recovery-2026-08-27.md`; `gh api repos/gmickel/stacks-api-smoke/pulls/6`
- Land today: the merge call is `gh pr merge <n> --squash --delete-branch --match-head-commit <sha>`; a head mismatch is `RESOLVING`; a moved base at the merge verdict stops the PR; the dependency contiguity check, the sibling re-gate after a merge, the tick lock with owner-aware stale takeover, and red-CI triage ordering shipped on 2026-08-29; land has no force-push capability and catch-up is the server-side `gh pr update-branch`. Source: land workflow, merge and gate sections; changelog for PR #378.
- **Head pin proven live, 2026-09-13**, on a fresh two-layer stack (PRs 9 and 10, stack 11) in the smoke repository. Stale `sha` on the bottom layer (the base commit instead of the head): HTTP 400, body `{"status":"failed","details":{"message":"Pull request head branch was modified."}}`, PR still open. Correct `sha` on the bottom layer: HTTP 202 `pending` with `expected_head_sha` equal to the pin, `merged` on the second three-second poll, squash commit returned in `details.sha`. GitHub then retargeted the upper layer to `main` and rewrote its head within three seconds; its timeline shows `automatic_base_change_succeeded` and `head_ref_force_pushed`, both attributed to the account that submitted the merge, not a bot. Stale `sha` on that retargeted layer (its pre-retarget head): HTTP 400, same body, PR still open. Correct `sha` on it: 202 then `merged` on the first poll. Source: `gh api repos/gmickel/stacks-api-smoke/pulls/9/merge-async`, `.../pulls/10/merge-async`, `.../issues/10/timeline`, `.../stacks/11`.
- **Patch-id survives the server retarget.** The upper layer's stable patch-id of base-to-head was identical before and after GitHub's rebase (`5b836022…` in both), which is the property R7 relies on. Source: `git diff <old base> <old head> | git patch-id --stable` versus the same over the new pair in the smoke clone.
- **Native merge leaves branches in place.** After both layers merged via merge-async, `refs/heads/pin-l1` and `refs/heads/pin-l2` still existed on origin. The branch janitor therefore applies on the native path exactly as on the plain path. Source: `git ls-remote origin` after the merges.
