## Goal & Context
<!-- scope: business -->

OpenCode (anomalyco/opencode) now implements the Agent Skills standard natively: it discovers `SKILL.md` skills from its own dirs and Claude-compatible dirs, has markdown-defined subagents dispatched via a Task tool, and markdown slash commands. It still has NO Claude-plugin format support (no marketplace, no `.claude-plugin/plugin.json`, no plugin `skills/`/`agents/`/`commands/` trees) — its own "plugin" system is JS event hooks, unrelated.

The existing OpenCode story is a separate community-port repo (`gmickel/flow-next-opencode`, last pushed 2026-01-23, seven releases stale). This spec replaces that route with an installer in THIS repo that scatters the canonical files into OpenCode's fixed directories — the same "canonical files, thin per-host delivery" pattern Cursor uses (blanket copy, no prose rewrite pass), not the Codex pattern (generated rewritten mirror).

Users get current flow-next on OpenCode from the canonical repo, riding every release; the maintainer stops owning a stale fork.

## Architecture & Data Models
<!-- scope: technical -->

**Delivery: `scripts/install-opencode.sh`** (POSIX bash, idempotent, snapshot-of-working-tree — same contract as `install-cursor.sh`). No canonical skill/agent prose changes (scoped claim: the SKILLS and AGENTS prose ships unmodified; setup is explicitly not supported on OpenCode in this spec — see the setup decision below). No sync-codex-style rewrite pass: canonical files ship AS-IS where OpenCode can consume them, and where the format genuinely differs (agents, commands) the installer GENERATES the target-format file from the canonical one at install time.

Target dir: `${XDG_CONFIG_HOME:-$HOME/.config}/opencode/` — **XDG only**; no `OPENCODE_CONFIG_DIR` probing. An explicit `--dest <path>` flag overrides the target for tests and non-standard setups (this is also what the deterministic tests drive).

Target layout:

**Pinned OpenCode directory layout:** the skills/agents/commands directory NAMES below are the plan's working assumption, not verified fact — OpenCode's documented convention may be singular (`agent/`, `command/`). The implementer pins the actual names from OpenCode docs/source at build time (same treatment as the agent schema), records the source reference in the installer, and the R2 manual live verification confirms the host actually DISCOVERS one installed agent and one installed command — file existence alone proves nothing, and every deterministic test is necessarily self-referential on these names. R7's docs claims are gated on that manual item.

- `skills/<skill-name>/` — canonical `plugins/flow-next/skills/*` copied as-is, EXCEPT `flow-next-setup/` (excluded — see the setup decision below; a description-matched dispatch into setup's platform cascade would land in the `else → codex` fallback even with no command stub). OpenCode reads `name`/`description` frontmatter and ignores unknown fields, so canonical frontmatter is already valid.
- **Plugin-root support dirs at the config root** — `scripts/` (flowctl + tracker package), `templates/`, `references/`, and `docs/`: everything canonical skill prose resolves plugin-root-relative at runtime (`${PLUGIN_ROOT}/templates/spec.md` tier-3 scaffold cascade, `${PLUGIN_ROOT}/templates/criteria.md`, `../../references/*`, docs cross-links). Two levels above any installed `skills/<name>/SKILL.md` is the opencode config root, so the EXISTING resolution rung ("plugin root derived from the skill's own SKILL.md absolute path, two levels up") finds all of them with zero prose changes. **Derivation rule (precise):** grep `${PLUGIN_ROOT}/` and `../../` across `skills/`, take the top-level path segments, then subtract a NAMED, reason-annotated exclusion list — host manifests (`.claude-plugin/`, `.cursor-plugin/`, `.codex-plugin/`), the Codex mirror (`codex/`), `skills/` itself (installed separately), and non-filesystem matches (e.g. URL fragments). The pin test asserts `derived − exclusions == installed support dirs` and fails when a NEW segment appears in neither set — a naive equality test fails day one, and resolving it the other direction would install the Codex mirror into the config root.
- `agents/flow-next-<name>.md` — GENERATED from canonical `plugins/flow-next/agents/*.md`: body after the closing frontmatter fence byte-identical; frontmatter translated per the **pinned OpenCode agent frontmatter schema** (see the schema decision below): `description` kept; `mode: subagent`; every canonical `disallowedTools` entry mapped to a denial the pinned schema can represent — the canonical token set is `Edit`, `Write`, `Task`, `Bash` (plan-sync carries `Bash`) and the generator FAILS CLOSED, with a named error and non-zero exit, on (a) any `disallowedTools` token without a mapping, (b) any denial with no representable target key in the pinned schema, and (c) a `readonly: true` that disagrees with the file's `disallowedTools` (readonly is the Cursor-native write-denial marker — permission-relevant, cross-checked, never silently dropped). Canonical `model:` family aliases are dropped (session-model inherit, same degradation as Cursor). Genuinely non-permission keys (`name`, `model`, `color`, `user-invocable`) are dropped, not fatal.
- `commands/flow-next-<name>.md` — GENERATED stub per skill-backed slash command. **Roster rule (single source of truth):** the set of canonical `plugins/flow-next/commands/<name>.md` files whose skill dir `plugins/flow-next/skills/flow-next-<name>/SKILL.md` exists (the mapping rule is exactly `commands/<name>.md` → `skills/flow-next-<name>/`; the stub filename is `flow-next-<name>.md` — the prefix is added once, never doubled). `commands/uninstall.md` is command-only (no skill dir): its body is copied verbatim as `commands/flow-next-uninstall.md` — it is self-contained and needs no skill. **`commands/setup.md` is excluded by name:** setup's platform-detection cascade has no OpenCode rung and falls through to `PLATFORM=codex`, which would write Codex-shaped instructions contradicting the installed stubs; no stub is generated, and the docs state plainly that `/flow-next:setup` is not supported on OpenCode yet and what to do instead (`flowctl init`, manual config keys). Every other stub: frontmatter `description` from the skill's own description; body instructs the agent to load and follow the installed skill's `SKILL.md` (absolute installed path) with `$ARGUMENTS` forwarded.

**Ownership manifest:** the installer writes ONE deterministic manifest (no timestamps, no host-varying absolute paths) at the config root listing EVERY installed path (skills dirs, generated agents, generated commands, scripts/, templates/, references/, docs/). Install-time `--delete` semantics, re-runs, and `--uninstall` all read from the manifest, never from the current source tree — so a skill renamed upstream between install and uninstall still gets cleaned, and "no writes outside owned paths" is assertable against a concrete list.

**Install pre-flight (fail closed):** if a target support dir (e.g. `<dest>/scripts/`) exists WITHOUT the ownership manifest claiming it, abort with a named error naming the colliding path; a documented `--force` flag overrides. A first install never deletes user-authored content to claim a path.

**Uninstall:** `--uninstall` removes exactly the manifest-listed paths and the manifest itself; a re-install after uninstall is byte-identical to a fresh install (guaranteed by the deterministic manifest).

**Asks:** canonical prose already carries the portable-host numbered-prompt fallback clauses required by the cross-platform checklist (AskUserQuestion is a Claude builtin invisible to Cursor/Droid/Grok too). OpenCode relies on those clauses; no rewrite.

## Edge Cases & Constraints
<!-- scope: technical -->

- Idempotent re-run = update; deletions within manifest-owned paths only.
- Never touch user content outside manifest-owned paths; never write into `~/.claude/` (OpenCode also reads it, but polluting Claude's own tree is the wrong home).
- The agent-frontmatter translation fails loudly per the three fail-closed cases above (unmapped token, unrepresentable denial, readonly/disallowedTools disagreement). An agent silently installed with broader write access than canonical intent is the one unacceptable failure mode — and it must be guarded on BOTH sides of the translation: unknown canonical input AND emitted keys outside the pinned target schema.
- CI: both `paths:` filter blocks of `.github/workflows/test-flow-next.yml` already carry a blanket `scripts/**` entry, so the new installer is covered from day one; add the explicit `scripts/install-opencode.sh` entry beside the other installers for parity/legibility only (both lists stay in step per `test_push_and_pull_request_filters_stay_in_step`).
- Ralph is OUT (deprecated harness; OpenCode hook system is incompatible anyway) — installer never registers hooks.
- Windows: out of scope initially (POSIX only, like the original cursor installer before the `.ps1` followed).

## Acceptance Criteria
<!-- scope: both -->

- **R1:** `scripts/install-opencode.sh` idempotently installs all canonical skills EXCEPT `flow-next-setup/` as-is under `<dest>/skills/` (dest = `${XDG_CONFIG_HOME:-$HOME/.config}/opencode` or `--dest`), plus the plugin-root support dirs (`scripts/`, `templates/`, `references/`, `docs/`) at the config root per the precise derivation rule; re-run after a canonical edit updates in place; paths removed upstream disappear from manifest-owned paths only. Pre-flight aborts with a named error when a target support dir exists unclaimed by the manifest (`--force` overrides).
- **R2:** the installed layout satisfies the CI-provable invariant: from every installed `skills/<name>/SKILL.md`, `../../scripts/flowctl` is executable and tracker-manifest-verified, and `../../templates/spec.md` exists. Separately, an explicitly MANUAL verification item — one live OpenCode session confirming (a) the host injects the skill's absolute path so the two-levels-up rung actually resolves, (b) the host DISCOVERS one installed agent and one installed command under the pinned directory names, and (c) which flowctl actually runs when a Codex install co-exists (`~/.codex/scripts/flowctl` wins the cascade's first rung on OpenCode — echo the resolved path) — gates the R7/R8 docs before they claim any of it works; the PATH-shim contingency is named in Decision Context if injection is absent.
- **R3:** every canonical `agents/*.md` yields a generated OpenCode agent file: body byte-identical; `mode: subagent`; every denial in the file's `disallowedTools` (full canonical token set: Edit, Write, Task, Bash) represented via keys from the pinned OpenCode agent schema; generation fails closed with a named error on an unmapped token, an unrepresentable denial, or a `readonly:`/`disallowedTools` disagreement; an invariant test fails when a new canonical `disallowedTools` token appears without a mapping.
- **R4:** every skill-backed canonical command yields a generated `commands/flow-next-<name>.md` stub (description from the skill, `$ARGUMENTS` forwarded to the installed SKILL.md path); `uninstall` is copied verbatim as command-only; `setup` is excluded by name with the exclusion stated in the generator; the roster rule and mapping rule are exactly as specified in Architecture.
- **R5:** `--uninstall` removes exactly the manifest-listed paths (plus the manifest) and nothing else; installing into a clean dest vs uninstall-then-reinstall produces byte-identical trees (deterministic manifest, no timestamps).
- **R6:** deterministic stdlib-unittest tests cover: the generator (fixture agent → expected pinned-schema frontmatter; the three fail-closed cases; command-stub generation incl. the uninstall-verbatim and setup-excluded cases), installer path-ownership (no writes outside manifest paths, pre-flight collision abort), the plugin-root read-surface pin (`derived − exclusions == installed support dirs`, failing on a new unhandled segment), and the layout invariant from R2 — all runnable in CI without an OpenCode install, driven via `--dest` into a temp dir. The explicit CI `paths:` parity entry lands in the same change (coverage already exists via `scripts/**`).
- **R7:** docs updated in the same workstream: `platforms.md` gains an OpenCode section (install command, installed layout incl. support dirs and manifest, limitations: no native ask primitive → numbered-prompt fallback; setup not supported — the setup SKILL is not installed and no stub exists, manual `flowctl init` + config instead; the slash form on OpenCode is flat `/flow-next-<name>`, mapping from the `/flow-next:<name>` form other docs use; a co-existing Codex install wins the flowctl cascade's first rung via `~/.codex` — noted explicitly; Ralph unsupported; model tiers inherit the session model), the root README install matrix row points at the installer instead of the port repo, and the community-ports table marks the old repo superseded. All claims that agents/commands/flowctl WORK on OpenCode are gated on the R2 manual verification. CHANGELOG `## Unreleased` entry staged in the repo; the docs-site changelog entry follows the format contract in `agent_docs/releasing.md` § "Docs-site changelog entry" including its `pnpm build` gate (committed separately in that repo).
- **R8:** the canonical platform sentence is updated by explicit decision recorded in Decision Context — OpenCode moves from "community port" to a named experimental install path, with first-class promotion explicitly deferred until the R2 manual verification plus a full dogfood run on OpenCode (the Grok-promotion bar). ALL restatement surfaces are updated in the same change: `platforms.md:3` (canonical), `README.md` (two occurrences), `CLAUDE.md` (sentence + the host-matrix OpenCode row), `STRATEGY.md` (two sentence occurrences, the "OpenCode port" mention, and the community-port adoption metric — the metric is restated in terms of the in-repo installer, since the port repo it measured is superseded), AND the flow-next.dev restatement surface named by `platforms.md:5` (updated in the docs-site repo under the same `pnpm build` gate as the changelog entry).

## Boundaries
<!-- scope: business -->

- No sync-codex-style rewritten mirror tree committed to the repo — the installer generates at install time from canonical files.
- No setup support on OpenCode in this spec: no detection rung, no generated setup stub — documented as unsupported with the manual alternative. (A `PLATFORM="unknown"` rung for setup's else→codex fallback is a separate spec; the hazard is pre-existing.)
- No Ralph/hook support on OpenCode.
- No Windows `.ps1` in this spec.
- No tier promotion to first-class in this spec — R8 defers it behind the manual live verification and a dogfood run.
- No archival/edits to the `flow-next-opencode` repo itself in this spec (separate housekeeping); this repo only updates its own references.

## Decision Context
<!-- scope: both -->

- **Installer over mirror:** OpenCode has no plugin format to mirror into; its consumption model is fixed directories. Cursor precedent (blanket copy, canonical as-is) fits; Codex precedent (committed rewritten mirror) does not.
- **Global config dir over project dirs:** flow-next is a toolchain, not per-repo content; per-project `.opencode/` installs would multiply staleness. Global matches how the Claude marketplace install feels. XDG only, `--dest` for tests — no undocumented env-var probing.
- **Support dirs at config root:** chosen precisely so the existing SKILL.md-relative resolution rung works untouched for EVERY plugin-root-relative consumer (scripts, templates, references, docs) — zero canonical skills/agents prose changes is a hard requirement (fn-197 copy-less doctrine). The install list is grep-derived and test-pinned, not hand-enumerated.
- **Pinned target schema for agents (round-1 review):** OpenCode's documented agent surface has both `tools:` (boolean map) and `permission:` (allow/ask/deny over a narrower key set). The implementation pins the actual key set from OpenCode docs/source at build time, records it in the generator, and prefers the representation that unambiguously covers write/edit/bash/task denial (expected: the `tools:` boolean map); fail-closed applies when a canonical denial has no representable key. Guarding only the input side while the output is silently ignored would be fail-open in disguise.
- **`readonly:` is permission-relevant:** it is the Cursor-native expression of a write denial (`test_cursor_agent_frontmatter.py` pins denies-Edit+Write ⇔ readonly). Cross-checked, never dropped as cosmetic.
- **Setup exclusion over detection rung (round-1 review, widened round 2):** shipping a stub that lands in setup's else→codex fallback misconfigures the user's repo on the first command they run — and excluding only the stub is one layer thinner than the hazard, because OpenCode dispatches skills by description match, so the installed SKILL remains phrase-reachable. The `flow-next-setup` SKILL is therefore excluded from the installed skill set entirely; docs state setup is unsupported with the manual alternative. A detection rung is deferred with the pre-existing else→codex fallback hazard.
- **Pinned directory layout (round-2 review):** the target dir names for skills/agents/commands are pinned from OpenCode docs/source at build time with the source recorded in the installer — a wrong name passes every self-referential CI test while OpenCode discovers nothing, so the R2 manual discovery check is the only honest gate.
- **Old port repo:** superseded, to be archived with a pointer in separate housekeeping once this ships (Gordon, 2026-08-20). The STRATEGY.md community-port metric is restated in installer terms in R8.
- **SKILL.md path-injection contingency (round-1 review):** if a live OpenCode session shows no absolute-path injection, the named fallback is a small `flowctl` PATH shim written by the installer; the docs claims stay gated on the manual verification either way.
- **Planning route (2026-08-20):** task breakdown drafted via a grok-4.6 read-only bridge on explicit user instruction; host validated, created, and owns the verdict. Plan review runs on the `host` backend (cross-family vs the grok writer).
